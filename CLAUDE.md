# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Or" (אור) — a Hebrew-first (RTL), 4-language (he/en/ru/ar) vacation-management PWA. The **entire application — HTML, CSS, and JavaScript — lives in one file: `index.html`** (~3400 lines). There is no separate JS/CSS, no framework, no bundler.

## Commands

There is no build step, package manager, linter, or test suite in this repo (no `package.json`). Development is: edit `index.html` directly, then open it in a browser (or preview via a static server) to check the result.

Deployment is a Cloudflare Worker with static assets (`wrangler.toml`: `main = "worker.js"`, `[assets] directory = "./" binding = "ASSETS"`) — not a Cloudflare Pages project, despite this repo's own history of assuming so; `[assets]` without `pages_build_output_dir` is the Workers-assets config shape, and an earlier `functions/api/*.js` file (the Pages Functions convention) silently 404'd in production for exactly this reason before being replaced with `worker.js`. Pushing to `main` deploys to production at `or.rlapp.net`. `index.html` has dead code checking for a `*.pages.dev` hostname to show a staging border — harmless, but it will never match; if/when this project's actual preview-URL mechanism is confirmed, fix that check to match it instead of removing it blind.

`wrangler.toml`'s `[assets]` also sets an explicit `include` allowlist (`index.html`, `version.json`, `terms.html`, `privacy.html`, `manifest.json`, `*.png`, `*.ico`) and `not_found_handling = "404-page"` — without this, the assets binding would serve *everything* in the repo root as a public static file, including `worker.js` itself, `.git/`, this worktree's own `.claude/` directory, and `wrangler.toml`. Adding a new public file (an icon, a new standalone page) means adding it to this list too, or it 404s in production even though it's right there in the repo.

There's also a **parallel, currently-unused `functions/` directory** (Pages Functions convention, one file per route, imported from `functions/_lib.js`) mirroring every route in `worker.js` — groundwork from an abandoned attempt to move this project to Cloudflare Pages (to work around a real, external Cloudflare bug where a Worker connected to GitHub loses dashboard-set secrets on every deploy: [cloudflare/workers-sdk#8871](https://github.com/cloudflare/workers-sdk/issues/8871)). The secrets issue got resolved directly on the Worker instead, so the Pages migration never happened - `functions/` is inert (Workers ignore that directory entirely) but has been kept in sync by hand since. **This is a real duplication-bug risk**: when touching any `/api/*` route, check whether the same fix is needed in both `worker.js` and its `functions/` mirror, or consider finally deleting `functions/` if the Pages migration is definitively off the table.

## Architecture

**Client-side data, no server persistence.** A local `api(url, opts)` function (inside `index.html`) fakes a REST API (`/api/records/:type`, `/api/trip`, `/api/bug`, etc.) but only ever reads/writes a single `localStorage` key (`STORE_KEY = 'or-store-v1'`). There is no server persistence — "saving" means the browser's own storage, an Excel export (SheetJS, loaded from CDN), or the optional Google Drive integration described below.

The one exception is `worker.js` (see deployment note above) — a thin router whose `fetch` handler special-cases a few `/api/*` routes and hands every other request straight to `env.ASSETS.fetch(request)`. Every route in it is stateless (no KV, no Durable Objects, nothing remembered between requests):
- `/api/link-preview` — a single server-side `fetch` of a pasted link, returning its Open Graph title/description/image, purely because the browser itself can't read another site's HTML cross-origin. No secrets needed. Called by `index.html`'s `fetchLinkPreviewInto()` from the trip's Links tab.
- `/api/google/exchange` and `/api/google/refresh` — see the Google Drive integration note below.
- `/api/chat` — see the AI trip assistant note below.

This is the app's only server-side code — everything else in this doc that says "fully client-side" is still true of the app's actual data.

**Data model — two parallel config objects drive everything:**
- `REC` — the record "shape" per data type (`flights`, `hotels`, `restaurants`, `cars`, `itinerary`, `tripexp`, `triplinks`): field list, which fields are numeric, which are enums, and the Excel sheet/column mapping. Consumed by the `api()` shim and by Excel export/import.
- `TOOLKIT` — the UI config for the same data types (plus a top-level `trip` entry): table columns, field types (`date`/`time`/`select`/`number`/`url`/`image`...), labels, `<select>` options.
- A **generic list-rendering engine** (`fieldHTML`, `listViewHTML`, `renderList`, `wireToolView`) reads both objects to render every data type's add/edit/delete form (in a popup `<dialog>`) and table. To add a field to an existing data type, edit `REC` + `TOOLKIT` together — don't hand-write new render code. This engine is the app's real reusable core; treat it as load-bearing infrastructure, not boilerplate to simplify away.

**i18n:** one `I18N` dictionary object, keyed by dotted strings (e.g. `'trip.dest.title'`), each entry holding `{ he, en, ru, ar }`. Look up with `t(key, vars)` (supports `{placeholder}` interpolation). `currentLang`/`applyLang()` swap the active language and re-sweep the DOM for `data-i18n` / `data-i18n-html` / `data-i18n-aria` / `data-i18n-ph` / `data-i18n-title` attributes. Every user-facing string must go through this dictionary — never hardcode display text. Dates/times always render via `fmtDate`/`fmtDateTime` (fixed dd/mm/yy, 24h) — deliberately independent of `currentLang` and of the visitor's OS/browser locale.

**Historical note on naming:** the app used to be a multi-tool platform (it had other tools — a building-committee manager, a home-expense ledger, etc. — transplanted from a sibling project) before being reduced to just this one `trip` tool. That's why some identifiers still read as generic multi-tool plumbing (`REC`, `toolData`, `currentTool`, `TOOLKIT.trip`, `showTool(id)`/`loadTool(id)` taking a tool-id parameter) even though `'trip'` is the only value that ever flows through them today. This is intentional, working config — not dead code.

**Google Drive integration** (`GOOGLE_CLIENT_ID`/`GOOGLE_API_KEY` consts, real credentials for a dedicated GCP project): uses Google Identity Services' popup-based **authorization-code** flow (`google.accounts.oauth2.initCodeClient` with `ux_mode: 'popup'`, not the plain implicit token flow) with the narrow `drive.file` scope — the app can only ever see files/folders it creates itself, never the user's other Drive content. `ux_mode: 'popup'` means no redirect URI is configured on the Google Cloud side (the special `redirect_uri: 'postmessage'` is used only in the server-side token exchange, per Google's convention for this flow — it is not a real URL). The one-time code the popup returns is exchanged server-side, via `worker.js`'s `/api/google/exchange` (needs the `GOOGLE_CLIENT_SECRET` secret — the whole reason a worker route exists here at all: only a server can hold that secret), for an access token **and a refresh token**. The refresh token is stored client-side (`localStorage`, key `or-drive-refresh-token`) — consistent with this app's no-server-persistence design, since there's no user-account/session concept to key server-side storage by anyway — and `driveEnsureToken()` uses it via `/api/google/refresh` to renew the access token silently (no popup) once per ~hour, falling back to a fresh popup only if there's no refresh token yet or it's been revoked. (Before this, the implicit flow's access token had no refresh token at all, so Or asked the user to reconnect every ~hour — this is what fixed that.) One external caveat that isn't visible from the code: a Google Cloud OAuth consent screen left in **Testing** publishing status caps refresh tokens at 7 days regardless of any of this; **Production** status doesn't expire them. That's a Cloud Console setting, not something this repo controls. The fixed Excel backup (`or-backup.xlsx`) lives at Drive root; user-uploaded PDF documents live in a separate, lazily-created Drive folder named after the trip (`tripFolderName()` / `driveFolderId()` / `driveUploadDocument()` / `driveListDocuments()`) — the two are independent, don't assume one implies the other.

**Multi-device backup conflict**: connecting Drive from a browser that already has its own local trip data would silently overwrite whichever side is older with no warning, which is exactly wrong when the same trip is being edited from two devices. `localBrowserHasTripData()` + `openDriveSyncDialog()` guard against this: the header's backup icon (`backupClockClick()`) only backs up immediately when this browser already has real data *and* Drive is already connected; otherwise (a fresh connect, or an empty local store) it opens a dialog showing both copies' last-saved times side by side, requires an explicit confirm checkbox, and only then enables "keep local" or "keep Drive" - never picks a side on its own.

**AI trip assistant** (`assistantToggle`/`assistantPanel` floating chat widget, always visible — unrelated to whether Google Drive is connected): `worker.js`'s `/api/chat` is a thin, stateless relay to an LLM, with a best-effort per-isolate rate limit (not a substitute for a real Cloudflare Rate Limiting Rule or a Google Cloud billing budget — see the comment above `chatHits`). All state — conversation history, and executing the model's tool calls — lives client-side in `index.html`'s `askAssistant()`: the client sends the running Gemini-format `contents` array plus `tools` (generated by `buildGeminiTools()` from `REC` for every record type, plus `list_trip_documents`/`read_trip_document` for PDFs in the current trip's Drive folder) and `systemInstruction` (built by `buildAssistantSystemInstruction()`, which also embeds a full snapshot of the current trip's data so the model can answer questions and find record ids without a separate read tool); when the model responds with a `functionCall`, the client executes it via `executeAssistantTool()` — which calls the exact same `api()` the manual add/edit forms use, so there is no separate/parallel write path — and loops the result back to the model. `delete_record` is the one destructive tool gated behind a `confirm()`, matching the manual delete button's own confirmation. Drive document reads remain limited to PDFs in Or's own per-trip folder and are performed client-side; the Drive token and raw file bytes are never sent to the model — only extracted text (and, if the user explicitly requests an "AI description" for a document, that text goes to whichever provider answers, per the privacy-policy disclosure this added).

**Gemini-only assistant**: `/api/chat` uses only Gemini (`GEMINI_API_KEY` secret, model in `GEMINI_MODEL`). There is no Cloudflare AI, NVIDIA, or other fallback path. The client and server use Gemini's native request/response format, so tool calls continue to work without an adapter or visible model-switching notice. Both `worker.js` and its inert `functions/` mirror must stay in sync here — see the deployment note above.

**Google Search grounding**: for a message `shouldUseGoogleSearch()` judges to be an open-ended lookup (e.g. "find a good restaurant near X"), the client sets `googleSearch: true` on the chat request; `askGemini()` then adds Gemini's built-in `googleSearch` tool so the model can ground its answer (and the record it might then add) in a real, current search rather than inventing one.

**Changelog convention**: every user-visible change must be logged in `CHANGELOG.md`, paired with a bump to `APP_VERSION` (near the top of the Drive-related consts in `index.html`) and the matching `version` field in `version.json` — these three stay in lockstep. The version number shown in the app's own Help dialog reads `APP_VERSION` directly.

**Standalone pages** `privacy.html` and `terms.html` at the repo root are separate static pages (no JS, no i18n) styled to match `index.html`'s theme, required for Google OAuth consent-screen verification. `index.html`'s footer links to both — Google's branding check crawls the home page for that link, so don't remove it without checking why it's there.
